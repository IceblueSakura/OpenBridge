# Chat Completions: single-candidate Generation admission

This is a bounded offline profile over the same Generation IR and reducer as Responses, not a second IR, a running gateway, or full Chat API compatibility. The fixed `openai==3.19.0` consumer in `tests/sdk/` supplies the independently checked `ChatCompletion`, `ChatCompletionChunk`, `CompletionCreateParams` and `ChatCompletionStreamOptionsParam` shapes (Apache-2.0 SDK). Version/source baseline: [upstream sync](../references/upstream-sync.md). This is schema/loopback evidence, not live Provider acceptance.

## Entry points and ownership

- `chat_envelope::decode_request_bytes` / `decode_response_bytes`: strict raw JSON plus complete envelope validation. Value overloads cannot validate lost raw-byte/duplicate-key information.
- `chat_envelope::encode_request` / `encode_response`: validated target representations from lowering, not raw JSON passthrough.
- `chat::decode_generation` and static response codecs remain task-level mappings.
- `ChatSseDecoder` / `ChatSseEncoder`: data-only SSE over the shared framer, strict JSON, event codec and reducer. No socket, credential, retry or tool execution.

`RequestContext` owns the public model label, `n`, `stream` and `stream_options`; these are not message history or upstream routing inputs. Request model binding must be resolved by the trusted caller, not by the codec. Reported response identity/model/created are validated separately rather than copied from request hints.

## Current admission

The table describes shared grammar and explicitly selected adapter rules, not a global vendor superset. The current profile-to-rule mapping lives in [`Adapter`](../../src/adapter/mod.rs); exact normalization contracts and rationale belong to [`WireRules`](../../src/protocol/adaptation.rs) and owning codecs/tests. Standard Chat rejects vendor carriers and usage aliases. The OpenBridge client extension permits readable reasoning and the scoped `openai-responses-v1` structured carrier; Provider selections must be read from code rather than inferred from this shared profile. Low-level protocol entry points use the standard profile.

Defaults are recorded outside task semantics, never override reported or malformed input, and never invent a whole usage object. A compatibility value is not a measured cache-write/billing fact; see [ADR 0008](decisions/0008-stable-core-and-vendor-adapters.md).

### Explicit message groups

The request/response `message_groups()` view borrows each assistant owner and its contiguous, explicitly attached function calls from final typed items. `ToolCall.message` is the membership authority, not array position; independent calls, reasoning and results are not inferred members. Whole-group reorder preserves identities, while removing an owner or moving a call outside its declared group requires explicit repair or rejection. Refusal and attached calls are mutually exclusive in static validation and at the first conflicting stream event. This view has no separate stored membership, turn identity or execution policy. Owners: [group view](../../src/semantic/task/generation/group.rs), [validation](../../src/semantic/task/generation/validate.rs), [reducer](../../src/semantic/task/generation/event.rs), [independent tests](../../tests/semantic/message_groups.rs).

### Text and refusal probabilities

Codec-only synthetic request example (the model label is not a catalog/instance claim):

```json
{"model":"synthetic-model","messages":[{"role":"user","content":"hello"}],"metadata":{"trace":"synthetic"},"service_tier":"auto","logprobs":true,"top_logprobs":1}
```

Chat request `logprobs` preserves absent/null/false/true; `top_logprobs` is optional (null normalizes to absent), an integer in 0..20 and requires `logprobs:true`. Responses projects the enabled control through its `include` entry; disabled/null boolean controls project to an omitted entry as inactive controls, not a fabricated response report. Removing controls from final IR removes their wire output.

Choice `logprobs.content` and `logprobs.refusal` attach to their matching text/refusal owner, never to tool arguments or reasoning. Missing/null carriers and null child arrays mean unreported; a present empty array is reported and preserved. Two active owners or a report without its matching part fail. Token/logprob and `top_logprobs` are required per reported token, with token/logprob required per top candidate. Byte representations are nullable/optional in Chat and are never inferred from token strings; encoding uses canonical null for absent byte details. Unknown keys, malformed counts/bytes, positive probabilities, over-budget arrays and wrong owners fail closed.

Static encoding and incremental deltas share typed owners. Final snapshots do not re-emit already delivered probabilities; retracting or enriching a previously delivered report fails rather than duplicating tokens or silently rewriting facts. Replacing text/refusal clears its dependent probabilities, and deleting probability metadata cannot resurrect source values. Response text probabilities project to Responses only with its required complete byte/top-token details; refusal probabilities have no Responses position and reject projection, including explicit empty arrays. Chat history has no choice probability carrier, so probability-bearing history cannot be silently emitted as plain messages.

Independent request/static/event/edit/failure oracles live in `tests/semantic/chat_logprobs.rs`; strict byte fragmentation and DONE closure live in `tests/transport/chat.rs`. Schema validation and model probability quality are different concerns.

### Reported token details

`Usage.input_text_tokens` and `output_text_tokens` map to the respective Chat detail object's `text_tokens`; `accepted_prediction_tokens` and `rejected_prediction_tokens` map to completion details. Missing/null detail values mean unreported (`None`), not zero; explicit zero stays reported and encodes as zero. Values are exact nonnegative integers bounded by the corresponding input/output total; accepted and rejected predictions are disjoint and their sum must fit output tokens without overflow. Rejected predictions still count toward output billing/limits. No counts are inferred from content or from another counter.

Text, reasoning, cache and prediction views need not be disjoint and are not added to derive totals. In particular a reported text count may already include reasoning ([documented text view](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions)); even an equal-to-total view is preserved, not discarded. Unknown/media counters still require their own admission. The shared [image slice](responses-text-profile.md#user-image-input) admits a typed image-token report only through explicit adapter slots; it is not a global vendor-field superset. The fixed Responses detail schema has no positions for text/prediction facts: any present value, including zero, fails static lowering and incremental Usage projection. No private fields or fidelity replay bypass that rejection. Removing those optional facts from typed IR removes them from wire; existing Responses cached/cache-write/reasoning usage remains projectable to Chat. Independent contracts are in `tests/semantic/usage.rs`.

### Function selection and tool results

Chat's `{"type":"allowed_tools","allowed_tools":{"mode":"required","tools":[{"type":"function","function":{"name":"lookup"}}]}}` maps to `ToolChoice::Allowed`, as does the flat Responses shell. Mode is auto/required, references must be unique, nonempty and declared; only function references project to Chat. The selection does not delete/reorder tool definitions, change strict defaults or enable custom/hosted execution.

A tool result's string and text-array forms remain distinct `ToolOutput` variants. Ordered parts, empty text and an explicit empty array survive decode, IR edits and encoding; unlike message arrays, a single tool-result part is not collapsed to a string. The tool call ID, not array position, binds the result. No concatenation, JSON argument parsing or media admission is implied.

### Scoped reasoning and unsupported fields

The scoped encrypted carrier maps to the same Responses-typed `ReasoningItem::encrypted` value and source/dependency proofs, not a second Chat token store. Deleting its typed value cannot restore ciphertext from fidelity. A complete encrypted detail closes its reasoning owner independently from the candidate finish: `length` or `content_filter` may leave that owner completed while the message/response is incomplete. Partial tokens and incomplete reasoning owners cannot be rendered as final encrypted details; both static and event lowering reject them without dropping or promoting the value. Plain `reasoning_content` alone remains readable text with no opaque-origin requirement, even when final message content is null. Independent regressions live in `tests/semantic/reasoning_boundary.rs`.

History field admission is role-specific: assistant refusal/reasoning fields (even null) on user/instruction/tool messages fail instead of disappearing during decode. Unknown fields are explicit errors, including presently unsupported standard fields. This table defines a subset, not a claim that those fields are nonstandard. Existing Responses-only semantics stay in the IR; an unavailable Chat projection must reject them rather than narrow the Responses contract.

### Provider stream shapes and normalization

An explicitly empty `tool_calls` array declares no calls and normalizes to absent, matching the streaming path; the model's text is never parsed into a call. A `tool_calls` list that is present and non-empty still requires complete call identity.

The fixed chunk schema permits missing/null continuation `function`, `name` and `arguments` fields: they carry no update after a call has been identified; the first call still requires its name and call ID. Null delta/call-identity fields likewise mean absent while a conflicting non-null identity fails. An opening empty `content`/`refusal` fragment defers the carrier message so readable reasoning keeps its static order, and the deferred empty part materializes at the terminal only when no other content won it (matching static `content: ""`). These are named stream normalizations over the same typed semantics: they change no IR meaning, drop no counts and never synthesize values.

## Output constraint shells

Chat `response_format` and Responses `text.format` map to the same `TextOptions.format` owner (`Presence<OutputConstraint>`); the shells are parsed and encoded independently and are not byte-isomorphic. Chat nests the schema body under a `json_schema` object, Responses places `name`/`description`/`schema`/`strict` beside `type`. `text` and `json_object` accept only `type`; unknown keys, unknown `type` values and wrong value types fail in both shells.

Outer presence follows the shared owner's rule that admitted child nulls and explicit defaults remain visible: a missing `response_format` is `Absent`; an explicit `null` is `Null` (present, not absent) and re-emits `null`; an object is `Value`. An explicit `{"type": "text"}` is the visible default: wire-distinct from omission and never synthesized from a missing or empty `text` container or verbosity-only settings. The pinned `openai==3.19.0` create type marks `response_format` non-nullable; admitting explicit null as a visible distinction is a local choice matching the shared `text.format` contract, not a claim that every server accepts it.

Inside the schema body the two shells share one field contract: `name` is required and bounded; `schema` is required and authoritative and fails rather than defaulting; `description` missing or null equals no description and is never re-emitted as null; `strict` missing or null is the general-structural mode with no filled default while an explicit `false` stays visible. Structural, strict and local-reference admission stays in the [schema profile](schema-profile.md); nothing here rewrites the schema.

A request constraint is not a response fact: Chat responses and chunks never echo `response_format` or settings. The mapping opens no other boundary: target structured-output capability and the Chat non-strict function default remain enforced; function `output_schema`, verbosity and truncation remain rejected. Logprobs follows its separate typed control and probability-owner contract above.

## Derived view replay

The pinned SDK's `ParsedChatCompletionMessage.parsed` sits beside `content` on assistant messages and derives from the message body. History replay admits the key on assistant messages only: missing or null is the SDK's no-view state and is dropped; a non-null view must equal, as a JSON value, the naive JSON parse of `content`, and a missing or null body cannot carry a non-null view. User/system/developer/tool messages reject the key outright. Static responses and chunks never carry or echo it: the typed `parsed` lives in the SDK client, not on the wire.

The view is validated then dropped following the shared [derived replay rules](responses-text-profile.md#derived-replay-views): it never enters the IR, is never emitted, and a replaced body cannot resurrect it. Function `function.parsed_arguments` follows the same rule against the authoritative `arguments` string on replayed assistant `tool_calls` and is dropped the same way. The SDK's chat stream accumulation also leaks the chunk `index` into message-level calls, and providers echo it on static messages: whenever present (static or replay) it must equal the call's position (the same ordinal rule the chunk layer enforces) and is dropped afterwards; a missing or null index is the plain shape. Static response call `index` may therefore be admitted as a checked representation artifact, but is never re-emitted. Derived `parsed`/`parsed_arguments` views stay rejected on upstream responses/chunks and are never echoed; they live in the SDK client, not on the wire.

## Delivery and terminal rules

`stream_options` objects require `stream=true`. Child options are optional booleans, not nullable: `include_usage` defaults false; `include_obfuscation` defaults true. The raw request presence is preserved independently of these effective defaults.

- With include_usage=true, the encoder requires an observed semantic Usage before terminal and emits the usage tail. With false, it omits the usage wire chunk without changing the semantic event/state. The decoder accepts a usage tail when reported; it does not invent one or infer the originating request's options.
- Padding is wire-only. Enabled encoding requires caller-supplied `Obfuscation::Seeded`; disabled delivery requires `Disabled`. The shared padding budget is charged before allocation. Decoding charges decoded UTF-8 padding before discarding it; exhausted budgets poison the stream. Synthetic seeds do not prove production entropy or side-channel resistance.
- `content_filter` maps to Incomplete/ContentFilter, independently of refusal content; `length` maps to Incomplete/MaxOutputTokens. Both retain partial output and are re-encoded distinctly, including through Responses incomplete_details. Unknown/unrepresentable reasons still fail rather than becoming length or success.
- finish_reason closes candidate output, not transport. Only a literal framed `data: [DONE]` closes the semantic stream. The encoder emits exactly one DONE after successful terminal encoding, never on cancellation/error or missing requested usage.
- SSE event names must be absent/empty or the default `message`. EOF requires a complete delimiter and DONE. Missing/early/duplicate DONE, malformed JSON, post-finish business data and post-DONE payloads cannot recover into success.
- HTTP admission requires 200 and text/event-stream with UTF-8 if a charset is specified. `SseLimits` independently limits single events, total wire, event count (including DONE) and aggregate padding. Shared JSON and semantic budgets additionally apply.

Callers retain unconsumed bytes from `consume`, finish framing before materializing, bound body collection and handle cancellation/backpressure. `Attempt` also consumes one frame per step and withholds the terminal until strict EOF. `ResponseDelivery` renders incrementally; the actual I/O caller explicitly marks commit/complete. These library mechanisms are not a production listener or automatic retry policy.

## Independent acceptance and remaining work

`tests/transport/chat.rs` covers independent static/event fixtures, fragmentation, request projection to Responses, output-constraint byte entry and dual-shell projection, final-event mutation, refusal/empty/length/content_filter, failure closure and resource limits. `tests/semantic/chat_wire.rs` covers `reasoning_content` typing/ordering, `system_fingerprint` presence and stream binding, usage aliases and terminal usage placement against independently authored wire. `tests/sdk/chat_text_loop.py` exercises SDK `parse()`/stream and typed chunks through function-tool turns with allowed-function selection, text-array tool results, reported text/prediction usage and a structured-output request, then replays the dumped derived views in later requests; the server synthesizes the final structured text from modified IR and asserts the replayed raw bodies stay authoritative. It does not claim model-output adherence or every parse branch. The existing Responses SDK gate remains separate; both use only synthetic loopback.

Function schemas use shared [structural/strict/reference validation](schema-profile.md); omitted Chat strict stays non-strict rather than adopting the Responses normalization default. Remaining standard text projections are classified in [implementation gaps](../implementation-status/generation.md#语义与表示缺口); they are selected by the end-to-end text scenarios in [next goal](../implementation-plans/next-goal.md), not an obligation to complete the whole Chat API before wiring the gateway. Media beyond the shared user image slice, multi-candidate output and production/Provider execution are outside this profile. See [next goal](../implementation-plans/next-goal.md) and [development commands](../development.md).
