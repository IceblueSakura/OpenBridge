# Responses v2: stateless Generation admission

This profile explains ownership and intentional admission boundaries, not the ceiling of the [Agent-first, protocol-neutral design](semantic-ir.md) or a promise that every Public Model admits every option. Exact wire rules and limits belong to [codecs](../../src/protocol/openai/mod.rs), [semantic types](../../src/semantic/task/generation/mod.rs) and independent fixtures. The [fixed standard baseline](../references/responses-standard.md) is distinct from local compatibility choices. [Implementation gaps](../implementation-status/generation.md) track unadmitted semantics, unwired carriers and audit scope; test execution results do not belong in this contract.

|---|---|---|---|
| `instructions`, ordered text messages, string `input` | Task `GenerationSettings` / ordered `Item` + stable parts | String input becomes one user text item; absent, null, empty instruction and multi-part developer/system instructions stay distinct where admitted; assistant `phase` labels are typed, status-independent and re-sent | Final task values encode the request; deleted items and part-bound breakpoints do not reappear |
| Function/custom tools, choice, calls, output | Task definition/policy and ordered call/result `Item` | Wire tool result may be text or text-part array. The shared IR also has bounded structured/error/image results, but this profile rejects their projection without an admitted carrier; SDK-derived `parsed`/`parsed_arguments` views follow the [derived replay rules](#derived-replay-views) and are not emitted | Call IDs and kind are checked; wrong association or unrepresentable Chat projection fails |
| Reasoning control, readable text, replay | Task policy / `ReasoningItem` parts and typed `encrypted` value; fidelity holds only source/dependency proofs | Missing/null/empty controls are not interchangeable; readable text has reasoning delta/done, not message content-part events | Replay requires matching trusted scope, unchanged dependencies, a final value and a completed owner; partial response output is not replayable history |
| `text.format`, verbosity, sampling and output limits | Task output constraint and generation controls | Text, JSON object and bounded JSON Schema have distinct typed controls; unknown controls fail; explicit `null` for non-nullable create-type controls (`text`, `tools`, `tool_choice`, `reasoning.mode`, Chat `parallel_tool_calls`) is rejected, never silently dropped | Re-derived requirements and target lowering must reflect final IR; inner schema is ordered JSON with shared [structural/strict/reference admission](schema-profile.md); it is not a general evaluator; reported settings echoes follow the response model instead: `text: null` collapses to absent and `reasoning.mode: null` stays visible |
| Text, refusal, citation and token probabilities | Typed response part and event reducer (refusal has its own probability owner for Chat) | `output_text.annotations` is required on request history, response output and content-part snapshots; missing or null is rejected, and an empty array stays visible. Responses has no refusal probability slot and rejects that projection |
| Reported usage and terminal | Task response/event terminal; adapter-owned normalization | Absent usage stays absent. Incomplete/error cannot become success |

## Response outcome and continuation

`GenerationResponse::outcome()` describes one response's completed/incomplete/failed/cancelled result. It does not encode a call/no-call distinction or assert logical-turn completion. For a completed response, the read-only `continuation()` view derives ordered pending call references from final items; a program with a matching subsequent output is not pending. No supported continuation fact means `Unreported`, never a fabricated end-of-turn. Non-completed responses do not offer this complete-response continuation view, even if an earlier item completed. Response item edits preserve outcome, usage and terminal details and recompute pending references; a completed response still rejects non-complete items.

`GenerationRequest::continuation()` applies the same pending-result relation to final ordered history. Function/custom/program calls resolve only against a subsequent result of the matching kind and call ID; names, adjacency and wire item IDs do not substitute for that association. Partial result arrival resolves only the corresponding calls, and edits recompute the remaining references in final call order. Request validation still rejects dangling, duplicate, wrong-kind or preceding results. A non-completed function call or in-progress tool/custom result leaves this complete-exchange view `Unreported`. A terminal result, including an incomplete artifact, reports an association, not successful tool execution or complete content.

The view is not another stored authority, does not parse arguments, and does not authorize execution. No pending calls (including after all results arrive) remains `Unreported`, not end-of-turn, a generate instruction or proof that group/opaque/settings dependencies are satisfied. History does not infer response/turn identity or change earlier response outcome, usage or terminal details. Neither Gateway scheduling nor wire admission is changed by querying this view; partial-history execution and broader continuation readiness require their own contracts. A pending program may exist in protocol-neutral history for dependency inspection, but Responses request decode and lowering require its matching reported output before wire replay. Standard grouping rejection remains binding.

Responses JSON/SSE keep their existing status and output fields, without a new continuation carrier. Chat finish labels retain their independent response-content consistency check. Owners: [response](../../src/semantic/task/generation/response.rs), [history](../../src/semantic/task/generation/request.rs), [continuation](../../src/semantic/task/generation/continuation.rs), [response regressions](../../tests/semantic/continuation.rs), [history regressions](../../tests/semantic/history_continuation.rs). Full turn/group/replay requirements remain [separate design gaps](../implementation-status/generation.md#语义与表示缺口).

## Message owners and cross-protocol grouping

Responses has no field corresponding to `ToolCall.message`. Request history and static response lowering reject any explicitly attached function call with `RepresentationError::MessageGrouping`; incremental projection rejects it at `ItemStarted`, before rendering the call. This includes Chat tool-only and text+tool groups, completed or partial output. Retaining the owner and call as separate items would still lose the relation through client delivery and history replay, so it is not a faithful standard mapping. No current profile declares a private membership carrier or an approved lossy conversion.

An independent empty assistant message remains a Responses item, preserving identity, phase and lifecycle. Independent function calls remain admitted even next to a message; decoding never infers membership from adjacency. Wire identity checks include empty owners. Such independently decoded message/call output may still fail single-candidate Chat projection; deleting the owner or silently attaching calls is not a repair. The named projection of a contiguous standalone-call run into a Chat call message is unchanged, but its resulting explicit membership cannot be projected back to standard Responses.

Rejection follows final typed membership after edits, not source coordinates. In an incremental stream, an earlier prefix may already be visible when the first attached call arrives; projection failure poisons the encoder, and HTTP delivery aborts without a successful terminal or fallback. Lack of a grouping carrier and broader group/replay dependencies remain [implementation gaps](../implementation-status/generation.md#语义与表示缺口), not implicit support. Independent request/static/event/edit oracles: [group projection](../../tests/semantic/group_projection.rs); group ownership: [Chat profile](chat-text-profile.md#explicit-message-groups).

## Reasoning replay authority

The typed reasoning owner retains the only Responses encrypted value, including opaque-only items. Item-start values are partial; item-done replaces or removes them. Static/event materialization includes the same value, and source fidelity cannot restore a deleted value or owner. Opaque and readable values share semantic aggregate limits; stream replacement releases the old value's charge. Opaque Debug is redacted, while dependency hashes still distinguish token-only edits. Scope binding and projection rules belong to [protocol/lowering](protocol-and-lowering.md#source-records); independent value, mutation and budget oracles are in [replay ownership tests](../../tests/semantic/replay_ownership.rs).

## User image input

The text-output profile also admits ordered user text/image content through the shared typed `Resource` owner. URL/inline sources and optional `ImageDetail` belong to final IR, not fidelity; source replacement, insertion, reorder and deletion cannot restore old media. The owning validation and limits are in [`resource.rs`](../../src/semantic/task/generation/resource.rs), wire mapping in [`image.rs`](../../src/protocol/openai/image.rs), and independent edit/failure oracles in [`images tests`](../../tests/semantic/images.rs).

Only HTTP(S) URLs and Base64 image data URLs are projected. File IDs require an issuer/resource lifecycle contract and remain rejected, as do instruction/assistant images, tool-result media and image output/events. Missing detail stays omitted; explicit auto remains explicit; null is rejected. Chat detail projection and Provider restrictions are checked during lowering rather than rewriting or silently dropping an unsupported value. No download, redirect, pixel parsing, OCR, resize or upload occurs in a codec. Media URL validation does not guarantee Provider-side fetch safety or availability; HTTP body limits remain independently tighter than the library limits.

Codec admission is not model admission: public/endpoint contracts and instance activation must be checked separately. The existing text response/event lifecycle is unchanged; accepting image input does not enable generated media or prove full multimodal standard coverage.

Reported `Usage.input_image_tokens` is a separate fact, not estimated from image size or added to cache/text counts. Its named Chat mapping is adapter-selected. The OpenBridge client explicitly extends `usage.input_tokens_details` (Responses) and `usage.prompt_tokens_details` (Chat) with optional `image_tokens`; missing/null means unreported, while zero is preserved. This is an OpenBridge wire extension, not a slot in the fixed standard Responses/Chat schema. A target without an admitted mapping rejects the report even at zero; typed edits/deletion affect both static and event output. Owning rules and independent closure tests are in [`adaptation.rs`](../../src/protocol/adaptation.rs) and [`image usage tests`](../../tests/semantic/image_usage.rs).

OpenBridge additionally declares optional `usage.input_tokens_details.text_tokens` and `usage.output_tokens_details.text_tokens` for typed reported input/output text counts. These are not fixed-standard Responses slots; standard targets still reject them even at zero. Named billing-view codecs validate duplicate totals and overlapping aliases, promote independent modality counts to `Usage`, and regenerate any native billing view from the final typed values after edits. Unknown breakdowns, tool charges and conflicting counters remain errors. See [`billing modality usage tests`](../../tests/semantic/billing_modal_usage.rs) for independent static/event, edit/deletion and failure oracles.

## Adapter admission

Low-level Responses entry points use the standard profile. Current Provider rule selections live in [`Adapter`](../../src/adapter/mod.rs), not a Markdown support matrix. Classified extras must remain bounded, scoped to protocol/adapter/origin, dependent on final response semantics and authoritative only at terminal. Derived views require validation before discard; protocol trailers cannot replace semantic terminals. Exact fields and normalization conditions are documented beside the owning codec and independent tests. These rules do not change standard task types or allow unknown keys.

## Complete-stream required fields

The complete Responses SSE boundary enforces structural presence: standard events and snapshots keep their required structure. Reported-fact normalization is a separate, explicitly selected adapter rule ([ADR 0008](decisions/0008-stable-core-and-vendor-adapters.md)). Every complete standard event carries `sequence_number` (integer, strictly increasing); `response.output_text.delta` and `response.output_text.done` additionally require a non-null `logprobs` array, including an explicit empty array when no probabilities are reported. Every complete Response snapshot carries the `output` array, where an explicit empty array is legal and an omission or `null` is not. The initial snapshot branches (`response.queued`/`response.created`/`response.in_progress`) require an empty `output` array, and the low-level snapshot branches apply the same completeness rule instead of backfilling a missing field. Ordering validation never substitutes for presence. The fixed source is the pinned SDK in [upstream sync](../references/upstream-sync.md); independent negative tests are in `tests/transport/responses_sse.rs` (complete byte entry) and `tests/semantic/` (snapshot branches), with the static entries sharing the same rule. The standard event grammar also rejects missing/null text probability arrays; the required empty event array does not invent optional static probability presence. A named adapter rule may interpret omitted text delta/done probability carriers as unreported; this does not add static probability presence, accept null/malformed arrays, or permit a missing done report after probabilities were reported. Canonical downstream events still include the required empty carrier. The independent scope/closure/poisoning oracles are in `tests/semantic/unreported_event_probabilities.rs`. Function/custom call IDs and function-call status follow their optional/nullable schema, unlike complete message headers. Independent admission regressions live in `tests/semantic/text_admission.rs`. Low-level pre-parsed event calls retain their existing optional sequence-number contract; complete byte entry always requires it. This does not claim every branch of the larger standard union is admitted or audited; see [audit gaps](../implementation-status/generation.md#验收缺口).

## Raw JSON admission

Use `envelope::decode_request_bytes` and `envelope::decode_response_bytes` for raw static bodies. `ResponsesSseDecoder` uses the same strict parser for each framed data payload. All reject duplicate object keys at any depth (including escape-equivalent names), invalid UTF-8/JSON and trailing non-whitespace data before semantic decoding. Embedded tool argument strings remain opaque; they are not recursively parsed as envelopes.

The parser admits at most `MAX_TOTAL_BYTES` (4 MiB) of input, including whitespace, before parsing. During parsing it permits at most 64 nested containers and 65,536 nodes, counting every value and object key. It does not allocate from collection size hints. Limits produce `CodecError::Limit`; syntax failures produce `CodecError::Invalid("JSON")` without echoing input. SSE failures poison the stream; fragmentation cannot bypass admission. SSE framing, aggregate wire and semantic budgets still apply independently.

Callers must separately bound HTTP body collection before passing an existing slice. Value-based codecs remain available for trusted/pre-parsed data but cannot prove original duplicate-key or raw-byte validity. These parser limits are distinct from the semantic [schema profile](schema-profile.md), which revalidates schema structure and local references.

## Derived replay views

The pinned SDK derives `parsed` (message text) and `parsed_arguments` (function arguments) client-side; the authoritative raw body is always the wire text or argument string. History replay (request `input` `output_text` parts and `function_call` items, plus the Chat message/tool-call shells) admits these keys as validated conveniences only: a missing or null view is the SDK's no-view state and is dropped; a non-null view must equal, as a JSON value, the naive JSON parse of the authoritative body — mirroring the SDK derivation over this opaque embedded string, not the envelope-strict JSON rules above. Values that cannot prove that derivation (pydantic dumps with coercion, aliases or filled defaults) and arbitrary SDK objects are rejected; a body that is not valid JSON cannot carry a non-null view.

Static response output and stream records reject derived views outright: upstream wire never carries them. The rules apply identically to both keys and both protocol shells, including Chat `tool_calls[].function.parsed_arguments`. Nothing is retained: views never enter the IR (`ToolCall.arguments` keeps only the raw string), are never emitted in requests, responses or events, and replacing the raw body can never resurrect an old view. The SDK's text_format/refusal derivation preconditions are not modeled; the commentary-`parsed` contradiction is rejected at message admission. Independent tests are in `tests/semantic/parsed_replay.rs`.

## Assistant phase labels

`phase: commentary | final_answer` is a standard assistant-message label, independent of item lifecycle status. Both static forms (typed item and shorthand message), request history and `response.output_item.added/done` snapshots admit and re-emit the label; the reducer carries it with the message so added/done snapshots must agree. Missing and null both mean unlabeled (the pinned SDK models them as one `None` state); no default label is synthesized and an unlabeled message never re-emits the key. Only assistant messages are labelled; user/system/developer messages and unknown values fail. The label has no Chat projection: Chat lowering rejects labelled messages instead of dropping the label, and a `commentary` message can never carry a non-null `parsed` view (the SDK never parses commentary text). Independent tests are in `tests/semantic/phase.rs`.

## Schema property order

`text.format.schema` and function `parameters/output_schema` retain object insertion order from raw JSON through IR and projection, including nested properties and reported JSON/SSE settings. The final IR is authoritative: replacing a property keeps its position, inserting a new property appends it, and deleting a schema or tool does not restore source values. Use order-preserving `retain` / `shift_remove` for removal; `serde_json::Map::remove` uses swap removal with `preserve_order` and may reorder survivors. This is not a guarantee of top-level envelope field order or original JSON whitespace.

Value callers must supply the intended order; neither the codec nor fidelity can recover order lost before admission. `Value` equality ignores object order, so order-sensitive acceptance compares key sequences or serialized schema, not equality/round trips alone. Independent tests are in `tests/semantic/schema.rs`. Chat limits: function parameters and `text.format` Structured Output project through the [Chat profile](chat-text-profile.md) shells, but function output_schema is still not admitted by Chat lowering.

The [schema profile](schema-profile.md) owns keyword shapes, strict/default modes, local-reference validation and separate resource bounds, based on the fixed [standard baseline](../references/responses-standard.md#4-tools-与-schema). Function output_schema does not inherit parameter strictness. Validation never rewrites property order, fills required or fetches a remote reference. Regex/format execution, model-specific restrictions and generated-output adherence are outside this admission.

## Control, message and annotation admission details

These rules apply to the current text subset; they do not admit additional standard branches.

| Branch | Required / presence rule | Normalization and rejection |
|---|---|---|
| Typed `TextOptions` in request or reported settings | `presence=false` requires both `format` and `verbosity` to be `Absent`; `Null` is present, not absent | Reject contradictory settings before lowering. `presence=true` with no children encodes `{}`; admitted child nulls and explicit defaults remain visible. Removing text requires removing its children, not hiding them |
| Complete response output message and HTTP/SSE item snapshots | Explicit `type:message`, nonempty bounded `id`, `role:assistant`, array `content`, and `status:in_progress/completed/incomplete` | Missing/null/invalid required values fail. Item/response lifecycle consistency is still checked separately; no synthesized upstream identity or status |
| Input message / low-level task snapshot | Existing abbreviated forms may omit id/status; existing content rules still apply | Keep lower-level normalization and explicit IR-to-wire identity synthesis separate from complete upstream validation |
| System/developer instruction message, including response instruction echoes | Omitted status and explicit `completed` normalize to a complete instruction without a lifecycle field. Typed `in_progress` and `incomplete` are stored on `Instruction.status` and re-emitted with `type:message` | Null, wrong type and unknown status fail. Non-complete status has no Chat projection. Shorthand messages still cannot carry status |
| Reasoning items on the wire | Required bounded non-null string `id` in request `input`, response `output` and SSE item snapshots | Upstream reasoning items without identity are rejected, never auto-completed; request encoding assigns fresh `item_{n}` identity to independently constructed items, so encoded requests re-decode |
| `configuration_update` | Ordered item, not a settings patch. Only `reasoning.effort` from the existing effort vocabulary; absent and null effort mean no update | Request `reasoning: null`, unknown keys and unknown effort fail. Response output and SSE snapshots require a bounded `id`; request `id` may be absent and is re-sent when present. The item never rewrites `GenerationSettings.reasoning`. Chat lowering rejects it |
| Function/custom dispatch | `async`, `defer_loading`, `allowed_callers`, call `namespace` and program `caller` are typed representation, not execution | Absent, null, `false`, empty namespace, `caller:direct` and `allowed_callers:["direct"]` stay omitted. Unknown values fail. Active values have no Chat projection |
| `program` / `program_output` items | Ordered typed items with required bounded `id`/`call_id` plus opaque `code`/`fingerprint` (program) or `result`/`status:completed|incomplete` (output); opaque values round-trip verbatim | Unknown keys and missing/null fields fail; non-terminal output status fails. Request replay requires exactly one output per program, named by a preceding program; program call IDs share the unique call-ID namespace with function/custom calls, and response output items stay self-describing. Event items are atomic: `output_item.added` carries the full opaque item and no output status, `output_item.done` owns the terminal status and must match. Request encoding assigns fresh `item_{n}` identity. Representation only, never execution; no Chat projection |
| `response.queued` lifecycle | At most one queued snapshot and only before `response.created`, under the initial grammar (`status:"queued"`, empty output, no usage/error/incomplete_details); `response.in_progress` requires a created response | Duplicate, post-created or malformed queued snapshots fail and poison the stream; a stream without a terminal still fails at EOF. The encoder re-emits `response.queued` from the same event flow. No Chat projection; static non-terminal response bodies (`queued`/`in_progress`) stay rejected with the background/state owner gap |
| Local compatibility | `reasoning.summary:false` is admitted and re-emitted by this profile. `response.cancelled` is a local terminal event | Neither is a pinned SDK standard value. `summary:false` is not a standard summary enum; `response.cancelled` is not a standard SSE event name |
| Cache hints (`prompt_cache_key`, `prompt_cache_options`, `prompt_cache_retention`) and independent identity hints (`safety_identifier`, `user`) | Typed request hints and reported echoes with distinct absent/null/explicit-value presence; `prompt_cache_options.prewarm` keeps omitted, `false` and `true` distinct | Hints are never copied into response facts; `service_tier` echoes the effective tier, retention (maximum policy) is never converted into `options.ttl` (minimum lifetime) and `user` is never aliased onto `prompt_cache_key`. `prewarm: null`, wrong types and unknown option keys fail. `prewarm` is representation only; its `generate` override is not modeled |
| OpenBridge cache grouping extension | The client Adapter admits a nonempty, control-free `session_id` string of at most 256 characters; the low-level standard codec does not | Target must explicitly admit the body carrier. No derivation from cache key/user/replay, no header passthrough, gateway session state or routing reorder. See [ADR 0011](decisions/0011-stable-admission-provider-cache.md) |
| Provider extension carrier ([ADR 0007](decisions/0007-stateless-cache-affinity-and-extensions.md)) | `CustomSections` round-trip beside the low-level request envelope; `CodexHeaders` is a separate typed/opaque header codec. | `response.output_text.annotation.added` | Required non-null typed `annotation`, correct owner/part/index | Missing/null/malformed payload rejects and poisons the decoder; a later terminal cannot recover it. Existing static-only `file_path` restriction remains |

`SseLimits::max_obfuscation_bytes` independently bounds aggregate decoded UTF-8 padding across the stream (default 4 MiB). Zero permits unpadded streams but rejects nonempty padding. Decoder charging is per framed payload, independent of input fragmentation; encoder charging happens before padding allocation. Exhaustion poisons the stream rather than silently disabling requested obfuscation. Single-event and total-wire limits still apply, including escaped JSON overhead. Seeded test padding proves neither production entropy nor a side-channel guarantee.

The `semantic` target covers field and transformation contracts; `transport` separately covers framing, Responses SSE and body lifecycle; the explicitly ignored `sdk_loopback` target exercises the locked Python consumer. Their modules and commands are described in the [development guide](../development.md). Codec and SDK loopback checks are not production wiring evidence. Media beyond the user URL/inline image slice, hosted tools, server-side conversation/background and real Provider execution are outside this admission. Remaining field/event gaps are tracked in [capabilities and boundaries](../implementation-status/generation.md); the active focus defines each slice's completion boundary. Production execution is outside this offline profile; the predecessor runtime is [archived](../archive.md).
