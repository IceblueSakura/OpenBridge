# 需求索引与阶段治理

OpenBridge 将长期产品目标、阶段目标与当前执行计划分开维护：

| 层级 | 回答的问题 | 位置 |
|---|---|---|
| 产品需求 | 产品必须支持什么、明确不支持什么 | [核心需求](proxy-requirements.md) |
| Provider 韧性需求 | 如何处理上游限流、临时失败、冷却、重试和最终错误 | [Provider 韧性需求](provider-resilience.md) |
| 阶段交付需求 | 以什么证据顺序收敛、每个阶段需要证明什么 | [阶段交付与研究需求](delivery-requirements.md) |
| 阶段契约 | 单个阶段的进入条件、范围、非目标、测试和退出条件 | [`docs/phases/`](../phases/README.md) |
| 当前实现 | 代码目前实际证明了什么 | [当前实现说明](../implementation/current-implementation.md) |
| 当前计划 | 当前 `Active` 阶段准备怎样完成 | [当前阶段实施计划](../plans/implementation-plan.md) |

## 单阶段规则

1. 任一时刻最多只有一个核心阶段为 `Active`。
2. `plans/implementation-plan.md` 只能展开该阶段，不得列出后续阶段的工作包、实现切片或预计任务。
3. 后续阶段只在阶段契约中保存目标、进入条件、非目标和退出条件；它们不是当前待办。
4. 已存在的跨阶段原型代码或测试证据不改变阶段状态。只有前置阶段 `Accepted` 且当前计划重新基线化后，下一阶段才能成为 `Active`。
5. 当前阶段完成后先关闭并记录证据，再单独建立下一阶段计划；不得在原计划末尾续写新 phase。

## 发现项分类

执行期间出现的新事项必须先分类：

| 分类 | 处理 |
|---|---|
| 当前阶段验收缺口 | 仅当它直接阻止既有退出条件时，才可加入当前计划，并说明对应需求/测试 ID。 |
| 需求变更 | 先修改产品需求或阶段契约，重新评估范围；不得直接追加实现任务。 |
| 后续阶段事项 | 写入对应阶段契约的候选说明，不进入当前计划。 |
| 核心后增强 | 写入 [`enhancements.md`](../phases/enhancements.md) 或专项增强需求，保持 `Deferred`。 |
| 缺陷但不阻塞当前阶段 | 进入独立 backlog；不因“顺手修复”扩大当前阶段。 |

新增发现本身不构成新 phase。只有出现新的、可独立验收的用户结果，并且无法归入现有阶段目标时，才允许先修改阶段交付需求，经过评审后新增阶段。

## 阶段状态

| 状态 | 含义 |
|---|---|
| `Draft` | 目标仍在需求层收敛，不能建立执行计划。 |
| `Blocked` | 进入条件未满足；可以保留研究或既有原型证据，但不能作为当前实现阶段推进。 |
| `Ready` | 进入条件满足，等待成为唯一 `Active` 阶段。 |
| `Active` | 唯一允许存在详细执行计划的阶段。 |
| `Accepted` | 退出条件已有可复现证据并完成阶段评审。 |
| `Deferred` | 不属于当前核心阶段链。 |

阶段状态与“当前代码实现了多少”是两个维度。实现事实只写入当前实现说明；阶段状态只由进入条件和退出证据决定。

## 修改要求

- 产品能力、外部行为或非目标变化：更新核心需求。
- 阶段目标、依赖、测试或退出条件变化：更新阶段交付需求及对应阶段契约。
- 当前阶段任务分解变化：只更新当前阶段实施计划。
- 已实现行为变化：更新当前实现说明。
- 任何文档都不得把计划、原型或研究结论表述为已验收能力。
